# 8.2 کوڈ کی صورت میں انفراسٹرکچر اور کنفیگریشن

## جائزہ اور محرکات

[Infrastructure as code](https://en.wikipedia.org/wiki/Infrastructure_as_code) (IaC) کا مطلب انفراسٹرکچر (نیٹ ورکس، سرور، ڈیٹا بیس، لوڈ بیلنسرز، اجازتیں) کو دستی کنسول کلکس یا ایڈہاک اسکرپٹس کی بجائے مشین سے پڑھی جانے والی تعریفی فائلوں سے متعین اور فراہم کرنا ہے۔ [Configuration management](https://en.wikipedia.org/wiki/Configuration_management) وہی خیال نظاموں کی ترتیبات اور حالت تک بڑھاتی ہے جب وہ موجود ہو جائیں۔ مل کر وہ انفراسٹرکچر کو ہاتھ سے بنے، نازک آرٹیفیکٹ سے اسی انجینئرنگ نظم و ضبط کی ورژن شدہ، قابل ریویو، قابل تکرار پیداوار میں بدلتی ہیں جو آپ ایپلیکیشن کوڈ کے لیے استعمال کرتے ہیں۔

بڑی ٹیموں کے لیے IaC سہولت نہیں ضرورت ہے۔ جب سینکڑوں انجینئروں کو ماحول چاہیے اور ہزاروں وسائل کو علاقوں اور اکاؤنٹس میں مستقل رہنا ہے تو دستی فراہمی ساتھ نہیں چل سکتی اور درست نہیں رہ سکتی۔ انسان سے ترتیب دیا انفراسٹرکچر دیر یا سویر منفرد "snowflake" سرورز میں بھٹک جاتا ہے جنہیں کوئی پوری طرح نہیں سمجھتا اور جو ناکامی کے بعد قابل اعتماد طور پر دوبارہ نہیں بنائے جا سکتے۔ انفراسٹرکچر کو مدون کرنا اسے مستقل، قابل آڈٹ، اور ڈسپوزیبل بناتا ہے۔ کوئی بھی ماحول اپنی تعریف سے دوبارہ بنایا جا سکتا ہے، اور کوئی بھی تبدیلی قابل ریویو diff ہے۔

انٹرپرائز اور سرکاری ادارے ایک اور فیصلہ کن فائدہ پاتے ہیں: قابل نفاذ نظم و نسق۔ سیکیورٹی اور تعمیل کے تقاضے، جیسے ذخیرے میں خفیہ کاری، نیٹ ورک کی تقسیم، منظور شدہ علاقے، اور لاگت کی تقسیم کے لیے tagging، براہ راست کوڈ میں سمائے اور کسی چیز کی فراہمی سے پہلے خودکار طور پر جانچے جا سکتے ہیں۔ انفراسٹرکچر کا بعد میں آڈٹ کر کے خلاف ورزیوں کا پیچھا کرنے کی بجائے، آپ غیر مطابق انفراسٹرکچر کو کبھی وجود میں نہیں آنے دیتے۔ شناخت سے روک تھام کی یہ تبدیلی بنیادی وجہ ہے کہ IaC جدید پلیٹ فارم کے عمل کی بنیاد بن گئی ہے۔

## بنیادی اصول

- قدموں کو بیان کرنے والے imperative اسکرپٹس پر مطلوبہ حالت بیان کرنے والی declarative تعریفوں کو ترجیح دیں۔
- تمام انفراسٹرکچر کی تعریفیں ورژن کنٹرول میں رکھیں، کسی بھی دوسرے کوڈ کی طرح ریویو شدہ۔
- انفراسٹرکچر کو ناقابل تغیر سمجھیں: جگہ پر بدلنے کی بجائے تبدیل کریں۔
- فراہمی کو idempotent بنائیں تاکہ وہی تعریف بار بار لاگو کرنا وہی نتیجہ دے۔
- drift، یعنی زندہ ماحول کا اپنی اعلان شدہ تعریف سے ہٹنا، مسلسل پہچانیں اور مصالحت کریں؛ سچ کا ماخذ کوڈ ہے، زندہ نظام نہیں۔
- انفراسٹرکچر کو کاپی اور پیسٹ کرنے کی بجائے دوبارہ قابل استعمال، ورژن شدہ modules سے ترتیب دیں۔
- پالیسی کو کوڈ کے طور پر مدون کریں، تنظیمی قواعد جو مشین سے جانچے جانے والے کوڈ کے طور پر ظاہر ہوں، تاکہ حفاظتی جنگلے مشورہ نہیں خودکار ہوں۔
- رازوں کو تعریفوں سے باہر رکھیں؛ انہیں مخصوص secrets manager سے حوالہ دیں۔

## سفارشات

### declarative ٹولنگ چنیں اور اسے modules کے گرد ترتیب دیں

[Terraform](https://en.wikipedia.org/wiki/Terraform_(software))، Pulumi، یا CloudFormation جیسا کلاؤڈ نیٹو اختیار، جیسا declarative IaC ٹول اپنائیں اور ادارے بھر اسے معیار بنائیں تاکہ آپ ٹولنگ کے بکھرے منظرنامے سے بچیں۔ کلیدی فن تعمیر کا عمل modularity ہے: چھوٹے، اچھی طرح دستاویزی، ورژن شدہ modules بنائیں جو عام نمونے گرفت میں لیں (مطابق نیٹ ورک، مضبوط بنایا گیا ڈیٹا بیس، معیاری سروس)۔ ٹیمیں پھر خام وسائل لکھنے کی بجائے ان modules سے ماحول ترتیب دیتی ہیں۔ یہ اچھے ڈیفالٹس اور سیکیورٹی کی ترتیبات خودکار پھیلاتا اور نقل کو ڈرامائی طور پر گھٹاتا ہے۔

### state کو دانستہ سنبھالیں

Declarative ٹولز کوڈ اور حقیقی وسائل کے درمیان نقشے کو state فائل میں ٹریک کرتے ہیں۔ state کو مشترک، خفیہ کردہ، رسائی کنٹرول شدہ backend میں دور سے رکھیں، اور locking استعمال کریں تاکہ ایک ساتھ تبدیلیاں اسے خراب نہ کر سکیں۔ کبھی state لیپ ٹاپ پر نہ رکھیں، اور آخری سہارے کی بحالی کی کارروائی کے سوا کبھی اسے ہاتھ سے ایڈٹ نہ کریں۔ state حساس ہے، کیونکہ اس میں وسائل کا میٹا ڈیٹا اور راز ہو سکتے ہیں، اس لیے اس کی اسی کے مطابق حفاظت کریں۔

### golden images کے ساتھ ناقابل تغیر انفراسٹرکچر بنائیں

چلتے سرورز کو patch کرنے کی بجائے، ورژن شدہ "golden image" (پہلے سے ترتیب شدہ، مضبوط بنائی گئی مشین یا کنٹینر image) بنائیں اور اس سے نئے instances ڈیپلائے کریں۔ جب آپ کو تبدیلی یا patch چاہیے تو نئی image بنائیں اور اسے رول آؤٹ کریں، پرانے instances ریٹائر کرتے ہوئے۔ یہ configuration drift ختم کرتا ہے، rollback معمولی بناتا ہے، اور ہر instance کو ایک جیسا اور معلوم اچھے بلڈ تک قابل سراغ رکھتا ہے۔ خودکار image pipelines میں سیکیورٹی کی مضبوطی اور اسکیننگ شامل ہو، تاکہ تعمیل image کی سطح پر ہی سمائی ہو۔

### configuration drift پہچانیں اور مصالحت کریں

Drift تب ہوتا ہے جب زندہ ماحول اپنی تعریف سے ہٹ جاتا ہے، عموماً اس لیے کہ کسی نے ہنگامی دستی تبدیلی کی۔ باقاعدہ drift کی شناخت چلائیں جو اصل حالت کا اعلان شدہ حالت سے موازنہ کرے اور فرق کو نشان زد کرے۔ drift کو نقص سمجھیں: دستی تبدیلی جگہ پر چھوڑنے کی بجائے کوڈ اپ ڈیٹ کر کے اور دوبارہ لاگو کر کے مصالحت کریں۔ جن نظاموں کو جاری configuration نفاذ چاہیے ان کے لیے configuration management ٹول استعمال کریں جو میزبانوں کو مسلسل ان کی اعلان شدہ حالت پر لائے۔

### GitOps اور pull پر مبنی ڈیپلائمنٹ اپنائیں

GitOps ماڈل میں، Git repository نظام کی اعلان شدہ مطلوبہ حالت رکھتی ہے، اور ہدف ماحول کے اندر چلتا خودکار agent مسلسل وہ حالت کھینچتا اور زندہ نظام کو اس سے ملانے کے لیے مصالحت کرتا ہے۔ یہ روایتی push ماڈل کو الٹتا ہے۔ ماحول بدلنے کے لیے کسی بیرونی نظام کو مستقل credentials نہیں چاہیے، کیونکہ ماحول اپنی کنفیگریشن خود کھینچتا ہے۔ GitOps آپ کو مکمل آڈٹ ٹریل (ہر تبدیلی commit ہے)، آسان rollback (commit revert کریں)، اور مضبوط drift کی اصلاح (agent مسلسل مطلوبہ حالت دوبارہ قائم کرتا ہے) دیتا ہے۔ یہ خاص طور پر [Kubernetes](https://en.wikipedia.org/wiki/Kubernetes) کے لیے اور ان اداروں کے لیے طاقتور ہے جو سچ کا واحد، قابل ریویو ماخذ چاہتے ہیں۔

### policy as code سے حفاظتی جنگلے نافذ کریں

تنظیمی قواعد، جیسے اجازت شدہ علاقے، لازمی خفیہ کاری، مطلوبہ tags، اور ممنوعہ عوامی نمائش، کو Open Policy Agent (OPA) جیسے ٹول یا Sentinel جیسے پلیٹ فارم کے اپنے policy انجن سے مشین کے جانچنے والی پالیسیوں کے طور پر ظاہر کریں۔ یہ جانچیں فراہمی سے پہلے pipeline میں چلائیں، تاکہ خلاف ورزیاں خودکار روکی جائیں۔ Policy as code سیکیورٹی ٹیم کے ارادے کو قابل عمل، یکساں لاگو کنٹرول میں بدلتا ہے، اور ہزاروں تبدیلیوں تک اس طرح پھیلتا ہے جیسے دستی ریویو کبھی نہ پھیل سکتا۔

## سمجھوتے: فوائد اور نقصانات

| انتخاب | فوائد | نقصانات | بہترین موزونیت |
|---|---|---|---|
| Declarative IaC (Terraform/Pulumi) | قابل تکرار، قابل ریویو، drift قابل شناخت | سیکھنے کا منحنی؛ state کے انتظام کی پیچیدگی | پیمانے پر تقریباً تمام ٹیمیں |
| Imperative اسکرپٹس | مانوس؛ ایک بار کے کاموں کے لیے لچکدار | idempotent نہیں؛ آڈٹ اور دہرانا مشکل | تنگ، عبوری معاملات |
| ناقابل تغیر + golden images | drift نہیں؛ rollback معمولی | image کی بلڈ pipeline کا اوور ہیڈ | مستقل مزاجی چاہنے والے بیڑے |
| قابل تغیر config management | باریک جاری کنٹرول | drift کا خطرہ؛ سست convergence | پرانے یا لمبی عمر کے میزبان |
| GitOps (pull پر مبنی) | مضبوط آڈٹ ٹریل؛ خود شفا | cluster کے اندر agent اور Git نظم و ضبط چاہیے | Kubernetes اور کلاؤڈ نیٹو |
| Policy as code | خودکار، یکساں حفاظتی جنگلے | پیشگی پالیسی لکھنے کی کوشش | ضابطے کے ماحول |

بنیادی کھنچاؤ لچک اور کنٹرول کے درمیان ہے۔ دستی اور imperative طریقے ایک تبدیلی کے لیے تیز لگتے ہیں، لیکن وہ چھپی عدم مستقل مزاجی جمع کرتے ہیں جو پیمانے پر معذور کر دیتی ہے۔ Declarative، ناقابل تغیر، پالیسی سے منظم انفراسٹرکچر زیادہ پیشگی سرمایہ کاری اور حقیقی ثقافتی تبدیلی مانگتا ہے، کیونکہ انجینئروں کو فوری کنسول تبدیلیاں کرنا چھوڑنا ہوتا ہے، لیکن وہ اس سرمایہ کاری کو قابل اعتمادی، قابل آڈٹ ہونے، اور کسی بھی چیز کو مانگ پر دوبارہ بنانے کی صلاحیت میں کئی گنا لوٹاتا ہے۔

## اپنی ٹیم کے ساتھ بحث کے سوالات

1. **مشترک module لائبریری کا مالک کون ہے، اور module میں بہتری ان کے استعمال کرنے والی ہر ٹیم تک کیسے پہنچتی ہے؟** Modules تبھی ادا کرتے ہیں جب اصلاحات اور مضبوط ڈیفالٹس پھیلیں، اور اس کے لیے واضح ملکیت اور حقیقی ورژننگ چاہیے، ایسا فولڈر نہیں جس سے سب کاپی کریں۔ طے کریں کہ مطابق نیٹ ورک اور مضبوط ڈیٹا بیس کے modules کون برقرار رکھتا ہے، آپ انہیں کیسے ورژن کرتے ہیں (changelog کے ساتھ semantic versioning)، اور ٹیمیں ہنگامی مشق کے بغیر اپ گریڈ کیسے کھینچتی ہیں۔ پیمانے پر یہ ایک بار misconfiguration ٹھیک کرنے اور ہزار ہاتھ سے ایڈٹ وسائل میں اس کا پیچھا کرنے کا فرق ہے۔ شہادت لائیں: آج ایک ہی نمونے کی کتنی الگ نقلیں موجود ہیں، سیکیورٹی کی اصلاح کو ہر ماحول تک پہنچنے میں کتنا وقت لگتا ہے، اور ٹیمیں module ورژن pin کرتی ہیں یا بہنے دیتی ہیں۔ اگر نازک patch دنوں میں پوری ملکیت تک نہیں پہنچ سکتا تو آپ کی modularity ظاہری ہے۔

2. **آپ کی drift کی شناخت کی تعدد کیا ہے، اور drift ملنے پر اصل میں کیا ہوتا ہے؟** Drift زندہ ماحول کا اپنی اعلان شدہ حالت سے خاموشی سے ہٹنا ہے، عموماً ہنگامی کنسول تبدیلی سے، اور اسے برداشت کرنا آپ کے کوڈ کو افسانہ بنا دیتا ہے۔ طے کریں کہ آپ کتنی بار اصل حالت کا اعلان شدہ حالت سے موازنہ کرتے ہیں (رات کو معقول ڈیفالٹ ہے) اور، زیادہ اہم، ردعمل طے کریں: کوڈ اپ ڈیٹ کر کے اور دوبارہ لاگو کر کے مصالحت کریں، کبھی دستی تبدیلی جگہ پر چھوڑ کر نہیں۔ ضابطے کی ترتیبوں میں یہ کنٹرول کا تقاضا ہے، کیونکہ آڈیٹرز کو چاہیے کہ اعلان شدہ حالت مسلسل حقیقت سے ملے۔ اپنے موجودہ اعداد لائیں: ہر ہفتے کتنے وسائل drift کرتے ہیں، کتنی دیر drift رہتے ہیں، اور انہیں بند کرنے کا کوئی جوابدہ ہے یا نہیں۔ ہر drift کو مالک والا نقص سمجھیں، ورنہ سچ کے ماخذ کی ضمانت گھلتی ہے یہاں تک کہ کوئی کوڈ پر بھروسہ نہیں کرتا۔

3. **کیا آپ GitOps اور pull پر مبنی مصالحت پر چلے گئے ہیں، یا کوئی بیرونی نظام اب بھی پروڈکشن بدلنے کے لیے مستقل credentials رکھتا ہے؟** Pull ماڈل میں ہدف ماحول کے اندر agent زندہ نظام کو Git سے مسلسل ملاتا ہے، جو کسی بیرونی نظام کے لکھنے کی رسائی رکھنے کی ضرورت ہٹاتا ہے، اور یہ مطلوبہ حالت دوبارہ قائم کرتا ہے تاکہ drift خود درست ہو۔ یہ مضبوط سیکیورٹی اور آڈٹ کی کیفیت ہے، کیونکہ ہر تبدیلی commit ہے اور کسی آپریٹر کو پروڈکشن کے مستقل credentials نہیں چاہییں۔ لاگت حقیقی ہے: چلانے کو cluster کے اندر agent اور سخت Git نظم و ضبط، اس لیے اسے اپنی موجودہ push پر مبنی خودکاری کے مقابل تولیں۔ فہرست لائیں کہ اس وقت کون اور کیا براہ راست پروڈکشن بدل سکتا ہے، اور وہ تبدیلیاں کون سی آڈٹ ٹریل چھوڑتی ہیں۔ Kubernetes اور اعلیٰ یقین دہانی کے enclaves کے لیے یہ تبدیلی عموماً قابل ہے؛ مٹھی بھر جامد وسائل کے لیے یہ ضرورت سے زیادہ ہو سکتی ہے۔

4. **آپ کی انفراسٹرکچر state کہاں ذخیرہ، locked، اور رسائی کنٹرول ہوتی ہے، اور جس دن وہ خراب یا کھو جائے اس دن کیا ہوتا ہے؟** State آپ کے کوڈ اور حقیقی وسائل کے درمیان نقشہ ہے، اس لیے کھوئی یا خراب state فائل ٹول کو ان وسائل سے اندھا چھوڑ سکتی ہے جو اس نے بنائے اور کسی کو تباہ کن دوبارہ لاگو کرنے پر اکسا سکتی ہے۔ بڑی ٹیم کے لیے خطرہ بڑھتا ہے، کیونکہ مشترک state کے مقابل لاگو کرنے والے بہت سے انجینئروں کو دور، خفیہ کردہ، locked backend چاہیے تاکہ ایک ساتھ رنز ایک دوسرے کو نہ کچلیں۔ ایک بڑی state کی سہولت کو اس کے بنائے دھماکے کے دائرے کے مقابل تولیں، اور state کو فی ماحول یا فی شعبہ تقسیم کرنے پر غور کریں تاکہ ایک غلطی سب کچھ نہ گرا دے۔ حقائق لائیں: state آج کہاں رہتی ہے، آیا locking نافذ ہے، اسے کون پڑھ سکتا ہے (اس میں راز ہو سکتے ہیں)، اور آیا آپ نے کبھی بحالی کی مشق کی ہے۔ انٹرپرائز اور سرکاری ترتیبوں میں state کے backend کو حساس، رسائی کنٹرول شدہ اثاثہ سمجھیں جس کا اپنا backup، آڈٹ لاگ، اور بحالی کا runbook ہو، کیونکہ اسے کھونا اس کا ریکارڈ کھونا ہے کہ کیا موجود ہے۔

5. **جب حقیقی ہنگامی صورت دستی تبدیلی مانگے تو منظور شدہ break-glass راستہ کیا ہے، اور وہ تبدیلی واپس کوڈ میں کیسے ضم ہوتی ہے؟** ہر پختہ IaC عمل آخرکار صبح تین بجے کے واقعے سے ملتا ہے جہاں pipeline کا انتظار قابل قبول نہیں، اور ایماندار سوال یہ نہیں کہ دستی تبدیلیاں کبھی ہوتی ہیں بلکہ یہ کہ آپ انہیں کیسے محدود رکھتے ہیں۔ پہلے سے طے کریں کہ pipeline کو کون bypass کر سکتا ہے، وہ کیا چھو سکتے ہیں، کارروائی کیسے لاگ ہوتی ہے، اور وہ آخری تاریخ جس تک تبدیلی کو کوڈ میں مصالحت یا واپس کرنا ہے۔ اس معاہدے کے بغیر ہنگامی استثنا خاموشی سے روزمرہ کی عادت بن جاتا اور ClickOps پچھلے دروازے سے لوٹتا ہے۔ شہادت لائیں: پچھلی سہ ماہی میں کتنی باہر کی تبدیلیاں ہوئیں، ہر ایک کتنی دیر غیر مصالحت رہی، اور آیا drift کی شناخت نے واقعی انہیں پکڑا۔ ضابطے اور عوامی اداروں کے لیے خودکار لاگنگ کے ساتھ دستاویزی break-glass طریقہ اکثر کنٹرول کا تقاضا ہے، کیونکہ آڈیٹرز توقع کرتے ہیں کہ ہنگامی صورتیں ممکن ہوں اور ہر ایک نشان چھوڑے اور نظام کو اس کی اعلان شدہ حالت پر لوٹائے۔

6. **آپ کی سیکیورٹی اور تعمیل کی بنیادی لائن کا کتنا حصہ پالیسی کے طور پر ظاہر ہے جو خراب تبدیلی خودکار روکتی ہے، بمقابلہ دستاویز میں رہنے والے قواعد جو کسی کے یاد رکھنے پر منحصر ہیں؟** Wiki میں نثر کے طور پر لکھے حفاظتی جنگلے معمول سے توڑے جاتے ہیں، کیونکہ وہ ہر انجینئر کے ڈیڈ لائن کے دباؤ میں انہیں پڑھنے اور لاگو کرنے پر منحصر ہیں، جبکہ وہی قواعد policy as code کے طور پر غیر مطابق تبدیلی کو فراہمی سے پہلے ہی مسترد کر دیتے ہیں۔ بڑے ادارے کے لیے یہی واحد راستہ ہے کہ سیکیورٹی ٹیم کا ارادہ ہزاروں تبدیلیوں تک ریویو کی رکاوٹ بنے بغیر پھیلے۔ پالیسیاں لکھنے اور برقرار رکھنے کی پیشگی لاگت کو دستی ریویو اور بعد میں اصلاح کی بار بار لاگت کے مقابل تولیں، اور طے کریں کہ کون سے کنٹرول (خفیہ کاری، منظور شدہ علاقے، لازمی tags، عوامی نمائش نہیں) اتنے غیر قابل مذاکرات ہیں کہ سخت دروازوں کے طور پر نافذ ہوں۔ اپنے موجودہ بنیادی قواعد کی فہرست لائیں اور نشان لگائیں کون سے خودکار بمقابلہ مشورتی ہیں، ساتھ یہ کہ عملاً ہر ایک کتنی بار توڑا جاتا ہے۔ انٹرپرائز اور سرکاری سیاق میں خودکار پالیسی آڈٹ کو ہفتوں کے دستی ثبوت جمع کرنے سے نافذ کنٹرولز کے مقابل query میں بدلتی ہے، اور تعمیل کو شناخت سے روک تھام میں بدلتی ہے۔

## شعبہ جاتی نقطۂ نظر

**اسٹارٹ اپ۔** رفتار جیتتی ہے، اس لیے اپنا پورا اسٹیک ایک declarative repository میں رکھیں (Terraform عام ڈیفالٹ ہے)، state منظم خفیہ کردہ backend میں رکھیں، اور تین افراد کی ٹیم کے ساتھ بھی ہر تبدیلی pull request سے گزاریں۔ بھاری پلیٹ فارم کا سازوسامان چھوڑیں: مرکزی module ٹیم نہیں، ابھی policy انجن نہیں، بس ورژن کنٹرول اور کنسول میں کبھی کلک نہ کرنے کا نظم و ضبط۔ یہی اکیلا آپ کو قابل تکرار ماحول دیتا ہے جنہیں آپ پیسے بچانے کو گرا اور اگلے ڈیمو کے لیے دوبارہ بنا سکتے ہیں۔

**چھوٹا کاروبار۔** مخصوص پلیٹ فارم ماہر کے بغیر، مخصوص ٹولنگ کھڑی کرنے کی بجائے منظم سروسز اور جو بھی IaC آپ کا کلاؤڈ فراہم کنندہ یا فروخت کنندہ پہلے سے سہارا دیتا ہے اس پر انحصار کریں جسے آپ برقرار نہ رکھ سکیں۔ ایسی golden-image pipeline بنانے پر جسے چلانے والا کوئی نہ ہو، ہوسٹڈ پلیٹ فارم خریدنے کو ترجیح دیں جس کے معقول ڈیفالٹس (خفیہ کاری، backups، patching) آپ کے لیے سنبھالے جائیں۔ ہدف تنگ تشکیل دیں: اپنے مٹھی بھر نازک وسائل کو کوڈ میں لائیں تاکہ آپ انہیں ناکامی یا رخصت ہوتے ٹھیکیدار کے بعد دوبارہ بنا سکیں۔

**بڑا ادارہ۔** بنیادی مسئلہ بہت سی ٹیموں، اکاؤنٹس، اور علاقوں میں مستقل مزاجی ہے، اس لیے ورژن شدہ مشترک module لائبریری، دور locked state، اور pipeline میں نافذ policy as code میں سرمایہ لگائیں۔ مرکزی پلیٹ فارم ٹیم مضبوط modules اور حفاظتی جنگلے شائع کرتی ہے جبکہ پروڈکٹ ٹیمیں ان کے اندر خود خدمتی کرتی ہیں، اور drift کی شناخت مسلسل چلتی ہے تاکہ ہزاروں وسائل معلوم حالت میں رہیں۔ modules اور پالیسیاں برقرار رکھنے کی جاری لاگت بجٹ کریں، کیونکہ ان کی قدر اصلاح یا مضبوط ڈیفالٹ کے ہر جگہ ایک ساتھ پھیلنے سے آتی ہے۔

**حکومت۔** خریداری کے قواعد، توثیق، اور عوامی جوابدہی آپ کو ناقابل تغیر انفراسٹرکچر، دستخط شدہ commits، اور توثیق شدہ enclave کے اندر GitOps مصالحت کی طرف دھکیلتے ہیں، تاکہ کوئی آپریٹر پروڈکشن بدلنے کے مستقل credentials نہ رکھے۔ مطلوبہ سیکیورٹی بنیادی لائن golden images اور policy as code میں مدون کریں، اور commit کی تاریخ کو چھیڑ چھاڑ ظاہر کرنے والے، مسلسل دستیاب آڈٹ ثبوت کے طور پر کام کرنے دیں۔ ملکیتی فارمیٹس پر کھلے، پورٹیبل ٹولنگ کو ترجیح دیں جو آپ کو پھنساتے ہیں، اور break-glass طریقہ اور اس کی لاگنگ واضح بنائیں تاکہ ہنگامی تبدیلیاں بھی configuration کنٹرول کے تقاضے پورے کریں۔

## مثالیں

**اسٹارٹ اپ۔** پانچ افراد کا اسٹارٹ اپ اپنا پورا AWS سیٹ اپ، یعنی VPC، ڈیٹا بیس، اور کنٹینر سروس، ایک Terraform repository میں متعین کرتا ہے، state خفیہ کردہ S3 backend میں اور locking DynamoDB سے۔ ہر تبدیلی pull request سے گزرتی ہے، اس لیے اکیلا on-call انجینئر بھی apply چلانے سے پہلے بالکل دیکھ سکتا ہے کہ کیا بدلے گا۔ جب انہیں بڑے ڈیمو کے لیے نیا staging ماحول چاہیے تو وہ چھوٹا module کاپی کر کے منٹوں میں کھڑا کرتے ہیں، اور کلاؤڈ کا بل کم رکھنے کو اتنی ہی تیزی سے گرا دیتے ہیں۔

**بڑا ادارہ۔** کثیر قومی خوردہ فروش کئی کلاؤڈ اکاؤنٹس اور علاقوں میں انفراسٹرکچر سنبھالتا ہے۔ مرکزی پلیٹ فارم ٹیم مطابق نیٹ ورکس، ڈیٹا بیسز، اور سروس کے ڈھانچے کے لیے ورژن شدہ Terraform modules شائع کرتی ہے، اور OPA پالیسیاں نافذ کرتی ہے جو خفیہ کاری یا لاگت کی تقسیم کے tags سے محروم کوئی بھی وسیلہ مسترد کرتی ہیں۔ پروڈکٹ ٹیمیں اپنے ماحول خود خدمتی سے فراہم کرتی ہیں، لیکن ہر تبدیلی pipeline سے گزرتی ہے، جہاں پالیسی خودکار جانچی جاتی ہے۔ Drift کی شناخت رات کو چلتی اور کسی بھی دستی تبدیلی پر ٹکٹ کھولتی ہے، ہزاروں وسائل کو مسلسل معلوم، مطابق حالت میں رکھتی ہے۔

**حکومت۔** اعلیٰ یقین دہانی کے ماحول میں کام کرتی دفاعی ایجنسی مضبوط golden images بناتی ہے جو مطلوبہ سیکیورٹی بنیادی لائن سموتی ہیں، اور صرف ان images سے ناقابل تغیر instances ڈیپلائے کرتی ہے۔ تمام انفراسٹرکچر Git میں اعلان ہے اور توثیق شدہ enclave کے اندر GitOps agent سے مصالحت ہوتا ہے، اس لیے کوئی آپریٹر براہ راست پروڈکشن بدلنے کے مستقل credentials نہیں رکھتا۔ ہر تبدیلی دستخط شدہ commit ہے۔ یہ آڈیٹرز کو مکمل، چھیڑ چھاڑ ظاہر کرنے والی تاریخ دیتا ہے اور دستی ثبوت جمع کیے بغیر مسلسل نگرانی اور configuration کنٹرول کے تقاضے پورے کرتا ہے۔

## کاروباری جواز: محرکات، ROI اور TCO

IaC کا ROI رفتار، قابل اعتمادی، اور خطرے میں کمی سے آتا ہے۔ جو ماحول پہلے ہفتوں کی ٹکٹ سے چلنے والی دستی فراہمی لیتے تھے وہ منٹوں میں بن سکتے ہیں، جو انجینئروں کو آزاد اور منصوبوں کو تیز کرتا ہے۔ قابل تکرار ہونا ناکامیوں کے بعد بحالی کا وقت بہت کم کرتا ہے، کیونکہ کوئی بھی ماحول کوڈ سے دوبارہ بنایا جا سکتا ہے۔ خودکار پالیسی کا نفاذ سیکیورٹی کے واقعات اور آڈٹ کے نتائج کی تعدد اور لاگت گھٹاتا ہے، جو ضابطے کے پابند اداروں کے لیے خاطر خواہ ہو سکتی ہے۔

TCO کے کھاتے پر، اپنانے کی لاگت میں ٹولنگ، تربیت، module اور پالیسی لائبریری بنانا، اور دستی تبدیلیاں بند کرنے کا نظم و ضبط شامل ہیں۔ نہ اپنانے کی لاگت زیادہ تیز ہے اور وقت کے ساتھ بڑھتی ہے: snowflake انفراسٹرکچر جو کوئی دوبارہ نہیں بنا سکتا، سست اور غلطی کی شکار فراہمی، سیکیورٹی کی misconfigurations جو خلاف ورزیوں تک لے جائیں، اور آڈٹس جو ہفتوں کی دستی کوشش کھائیں۔ قیادت کے لیے IaC کو انفراسٹرکچر کو غیر منظم ذمہ داری سے منظم، قابل تکرار اثاثے میں بدلنے کے طور پر پیش کریں، اور اس میکانزم کے طور پر جو سیکیورٹی اور تعمیل کو خواہشی کی بجائے خودکار بناتا ہے۔

## ضد نمونے اور خامیاں

- **پروڈکشن میں ClickOps۔** کنسول میں ہاتھ سے تبدیلیاں کرنا drift کی ضمانت دیتا اور قابل تکرار ہونا تباہ کرتا ہے۔
- **کوڈ میں راز۔** تعریفی فائلوں میں credentials ہارڈ کوڈ کرنا انہیں ورژن کی تاریخ اور state میں لیک کرتا ہے۔
- **یک سنگی، غیر modular تعریفیں۔** ایک بہت بڑی کنفیگریشن جسے بدلنے کی کوئی ہمت نہ کرے اس دستی سیٹ اپ جتنی نازک ہو جاتی ہے جس کی جگہ اس نے لی۔
- **غیر منظم state۔** مقامی یا unlocked state فائلیں خرابی اور کھوئے انفراسٹرکچر کی طرف لے جاتی ہیں۔
- **برداشت شدہ drift۔** دستی تبدیلیاں جگہ پر چھوڑنا سچ کے ماخذ کی ضمانت کو گھساتا ہے یہاں تک کہ کوڈ افسانہ ہو جائے۔
- **دستاویز کے طور پر پالیسی۔** وہ قواعد جو خودکار جانچ کی بجائے wiki میں رہتے ہیں معمول سے توڑے جاتے ہیں۔
- **کاپی-پیسٹ کا پھیلاؤ۔** ٹیموں میں کنفیگریشن کی نقل کا مطلب ہے کہ اصلاحات اور بہتریاں کبھی نہیں پھیلتیں۔

## پختگی کا ماڈل

**سطح 1: آغاز۔** انفراسٹرکچر کنسول اور ایڈہاک اسکرپٹس سے دستی فراہم ہوتا ہے۔ ماحول غیر مستقل، غیر دستاویزی ہیں اور قابل اعتماد طور پر دوبارہ پیدا نہیں ہو سکتے، اور ناکامی سے بحالی سست اور غیر یقینی ہے۔

**سطح 2: ترقی۔** کچھ انفراسٹرکچر مدون ہے، لیکن عمل ٹیم کے لحاظ سے مختلف ہیں۔ State کا انتظام غیر مستقل ہے، drift عام ہے، راز کبھی کبھار تعریفوں میں لیک ہوتے ہیں، اور پالیسی، اگر ہو، تو دستی ریویو سے نافذ ہوتی ہے۔

**سطح 3: معیار بندی۔** Declarative IaC ادارے بھر دستاویزی معیار ہے، مشترک ورژن شدہ modules سے بنا، منظم، دور، locked state کے ساتھ۔ Policy as code pipeline میں حفاظتی جنگلے نافذ کرتا ہے، راز مخصوص manager سے حوالہ دیے جاتے ہیں، اور drift کی شناخت باقاعدہ وقفے پر چلتی ہے۔

**سطح 4: انتظام۔** عمل بنیادی خطوط کے مقابل ناپا جاتا ہے۔ آپ drift کی شرح اور مصالحت کا اوسط وقت، ٹیموں میں module کے ورژن کا اپنانا، روکی بمقابلہ فرار ہوئی پالیسی کی خلاف ورزیاں، فراہمی کا lead time، اور وسائل کا وہ حصہ جو واقعی کوڈ کے تحت ہے ٹریک کرتے ہیں۔ یہ میٹرکس تبدیلیوں پر دروازے لگاتی اور سرمایہ کاری کی سمت طے کرتی ہیں، اس لیے فیصلے واقعاتی کہانیوں کی بجائے شہادت پر ٹکتے ہیں۔

**سطح 5: ہم آہنگی۔** انفراسٹرکچر ناقابل تغیر اور GitOps سے چلتا ہے، drift کے مقابل خود شفا، تعمیل کے ثبوت خودکار پیدا ہوتے ہیں۔ Module اور پالیسی لائبریری حقیقی استعمال اور واقعات سے مسلسل بہتر ہوتی ہے، اور انفراسٹرکچر کا عمل سیکیورٹی، لاگت، اور ترسیل کی منصوبہ بندی سے مربوط ہے تاکہ تقاضے بدلنے پر پوری ملکیت ڈھلے۔

## بحث کے لیے خیالات

- مرکزی طور پر منظم modules اور اپنی مرضی کا انفراسٹرکچر متعین کرنے کی ٹیم کی خودمختاری کے بیچ لکیر کہاں ہونی چاہیے؟
- ClickOps کو معمول بنائے بغیر اس حقیقی ہنگامی تبدیلی کو کیسے سنبھالیں جسے pipeline bypass کرنا ہو؟
- بہت سے اکاؤنٹس اور ٹیموں میں state کو منظم اور محفوظ کرنے کی درست حکمت عملی کیا ہے؟
- قابل تغیر configuration management کب بھی جائز ہے بمقابلہ مکمل ناقابل تغیر انفراسٹرکچر؟
- آپ policy-as-code لائبریری کو بدلتے سیکیورٹی اور ضابطے کے تقاضوں سے ہم آہنگ کیسے رکھتے ہیں؟
- اس پرانے انفراسٹرکچر کے لیے جو IaC سے پہلے کا ہے حقیقت پسندانہ منتقلی کا راستہ کیسا لگتا ہے؟

## اہم نکات

- انفراسٹرکچر کو declarative طور پر متعین کریں، ورژن کریں، اور اسے قابل ریویو، قابل تکرار کوڈ سمجھیں۔
- اچھے ڈیفالٹس پھیلانے اور نقل ختم کرنے کو چھوٹے، ورژن شدہ modules سے بنائیں۔
- drift مٹانے اور rollback سادہ کرنے کو ناقابل تغیر انفراسٹرکچر اور golden images کو ترجیح دیں۔
- state دانستہ منظم کریں اور رازوں کو تعریفوں سے باہر رکھیں۔
- مضبوط آڈٹ ٹریل اور خود شفا مصالحت کے لیے GitOps اپنائیں۔
- حفاظتی جنگلے policy as code سے نافذ کریں تاکہ تعمیل بعد میں آڈٹ ہونے کی بجائے روک تھام سے وجود میں آئے۔
