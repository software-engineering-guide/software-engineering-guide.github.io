# 2.3 APIs اور انٹرفیس ڈیزائن

## جائزہ اور محرکات

[API](https://en.wikipedia.org/wiki/API) (ایپلیکیشن پروگرامنگ انٹرفیس) وہ معاہدہ ہے جس کے ذریعے سافٹ ویئر کا ایک ٹکڑا دوسرے کو صلاحیت پیش کرتا ہے۔ یہ وہ جگہ ہے جہاں ٹیمیں، نظام اور ادارے ملتے ہیں، اور یہ غلط کرنے کے لیے سب سے زیادہ پائیدار اور مہنگی چیز ہے۔ آپ اندرونی فنکشن کے دستخط کو آزادانہ ری فیکٹر کر سکتے ہیں۔ شائع شدہ API مختلف ہے: یہ ان صارفین سے وعدہ ہے جن سے آپ کبھی نہ ملیں، اور اسے توڑنا انہیں توڑنا ہے۔ جیسے ادارے [یک سنگی](https://en.wikipedia.org/wiki/Monolithic_application) نظاموں کو سروسز میں توڑتے ہیں اور شراکت داروں اور عوام کے لیے صلاحیتیں کھولتے ہیں، API مرکزی پروڈکٹ سطح اور مرکزی انضمام کا خطرہ بن جاتی ہے۔

بڑی ٹیموں کے لیے APIs ہی وہ چیز ہیں جو لوگوں کو آزادانہ کام کرنے دیتی ہیں۔ اچھی طرح ڈیزائن شدہ انٹرفیس آپ کو ہر صارف کے ساتھ ہم آہنگی کیے بغیر اپنا اندرونی حصہ بدلنے دیتا ہے، جو سروس کی حد کا پورا مقصد ہے۔ خراب ڈیزائن شدہ انٹرفیس اندرونی تفصیل لیک کرتا ہے، ہم قدم تعیناتی پر مجبور کرتا ہے، اور سروسز کے سیٹ کو تقسیم شدہ یک سنگی میں بدل دیتا ہے: سروسز جو الگ ہو گئیں مگر اتنی جڑی ہوئی کہ انہیں اکٹھے بنانا اور تعینات کرنا پڑتا ہے۔ آپ کا API ڈیزائن براہ راست طے کرتا ہے کہ آپ کی ٹیمیں کتنی آزادی سے حرکت کر سکتی ہیں۔

انٹرپرائز اور سرکاری ماحول میں APIs تعمیل، سلامتی اور طویل العمری کی ذمہ داریاں بھی اٹھاتی ہیں۔ سرکاری شعبے کی API سے تقاضا ہو سکتا ہے کہ [کھلے معیارات](https://en.wikipedia.org/wiki/Open_standard) کی پیروی کرے، برسوں مستحکم رہے، اور ایسے بیرونی ڈویلپرز کی خدمت کرے جن سے آپ ہم آہنگی نہیں کر سکتے۔ انٹرپرائز APIs معاہداتی سروس کی سطحوں کے ساتھ شراکت داروں کے انضمام کی بنیاد ہیں۔ یہ سب ورژننگ کے نظم و ضبط، [پسماندہ مطابقت](https://en.wikipedia.org/wiki/Backward_compatibility)، نظم و نسق اور ڈویلپر تجربے کا معیار بلند کرتا ہے۔

## بنیادی اصول

- پہلے معاہدہ ڈیزائن کریں۔ انٹرفیس سوچا سمجھا پروڈکٹ فیصلہ ہے، نفاذ کی ضمنی پیداوار نہیں۔
- صارف کے تجربے کے لیے بہتری لائیں، اپنی سہولت کے لیے نہیں۔
- پسماندہ مطابقت کو وعدہ سمجھیں۔ توڑنے والی تبدیلیوں کو نیا ورژن اور منتقلی کا راستہ چاہیے۔
- آسان چیز کو درست بنائیں: معقول ڈیفالٹس، قابل پیش گوئی خرابیاں، مستقل اصول۔
- ناکامی کے لیے ڈیزائن کریں۔ [ایڈمپوٹنس](https://en.wikipedia.org/wiki/Idempotence) (دہرائی گئی درخواست کا وہی اثر جو ایک کا ہو)، دوبارہ کوششیں، صفحہ بندی، اور [شرح کی حد](https://en.wikipedia.org/wiki/Rate_limiting) اولین تشویشات ہیں، بعد کے خیال نہیں۔
- پروٹوکول کا انداز تعامل کے مطابق چنیں، فیشن کے مطابق نہیں۔
- APIs کو مصنوعات کی طرح منظم کریں، مالکوں، لائف سائیکل اور دستاویزات کے ساتھ۔

## سفارشات

### پہلے API اور معاہدے پر مبنی کام کریں

نفاذ لکھنے سے پہلے API کا معاہدہ، بشمول اس کے وسائل، عملیات، اسکیماز اور خرابی کے معنی، متعین اور ریویو کریں۔ مشین سے پڑھے جانے والی تصریح استعمال کریں، تاکہ معاہدہ دستاویزات، کلائنٹ اور سرور کے اسٹبز، نقلی سرورز اور توثیق پیدا کر سکے۔ اب صارفین آپ کے بناتے وقت نقلی کے خلاف انضمام شروع کر سکتے ہیں، اور معاہدہ سچائی کا واحد ماخذ بن جاتا ہے جس کے خلاف دونوں فریق ٹیسٹ کرتے ہیں۔

### تعامل کا انداز سوچ سمجھ کر چنیں

[REST](https://en.wikipedia.org/wiki/REST) (نمائندگی کی حالت کی منتقلی)، [GraphQL](https://en.wikipedia.org/wiki/GraphQL)، [gRPC](https://en.wikipedia.org/wiki/GRPC) اور [ایونٹ پر مبنی پیغام رسانی](https://en.wikipedia.org/wiki/Event-driven_architecture) میں سے تعامل کی بنیاد پر چنیں، ذاتی ترجیح پر نہیں۔ وسائل پر مبنی، وسیع طور پر قابل تعامل، کیش ہونے کے قابل انٹرفیسز کے لیے REST استعمال کریں۔ جب متنوع کلائنٹس کو بھرپور گراف پر لچکدار، مجموعی پڑھت چاہیے ہو تو GraphQL استعمال کریں۔ اندرونی سروسز کے درمیان اعلیٰ کارکردگی، مضبوط ٹائپ شدہ کالز کے لیے gRPC استعمال کریں۔ غیر ہم وقت، ڈھیلے جڑے ورک فلو اور حالت کی تبدیلیاں پھیلانے کے لیے ایونٹ پر مبنی پیغام رسانی استعمال کریں۔ بہت سے بڑے نظام کئی اسلوب ایک ساتھ استعمال کرتے ہیں، ہر ایک وہاں جہاں موزوں ہو۔

### نظم و ضبط کے ساتھ ورژن بنائیں اور متروک کریں

واضح ورژننگ کی حکمت عملی اور شائع شدہ متروک کرنے کی پالیسی اپنائیں: آپ تبدیلیوں کی درجہ بندی کیسے کرتے ہیں، پرانے ورژن کتنی دیر سپورٹ کرتے ہیں، اور صارفین کو کیسے اطلاع دیتے ہیں۔ پسماندہ مطابقت والی تبدیلیوں (اختیاری فیلڈز یا نئے اینڈ پوائنٹس شامل کرنا) اور توڑنے والی تبدیلیوں (فیلڈز ہٹانا یا نام بدلنا، اقسام یا معنی بدلنا) کے درمیان صاف لکیر کھینچیں۔ موجودہ فیلڈ کے معنی کو کبھی دوبارہ مقصد نہ دیں۔ صارفین کو منتقل ہونے کے لیے ملاپ کی کھڑکیاں دیں، اور وقت کی حدیں پہلے سے اچھی طرح بتائیں۔

### خرابی کے معنی مستقل اور مشین سے پڑھے جانے والے بنائیں

منظم، قابل پیش گوئی خرابیاں واپس کریں: مستحکم مشین سے پڑھے جانے والے کوڈ، انسانی پڑھنے کے پیغامات، اور عمل کرنے کے لیے کافی سیاق، حساس اندرونی چیزیں لیک کیے بغیر۔ ہر اینڈ پوائنٹ پر وہی حالت کے معنی استعمال کریں، تاکہ کلائنٹس خرابیاں یکساں طور پر سنبھال سکیں۔ ہر وہ خرابی دستاویزی کریں جس کا صارف کو سامنا ہو سکتا ہے۔

### ایڈمپوٹنس، صفحہ بندی اور شرح کی حد شامل کریں

ایڈمپوٹنس کیز کی حمایت کر کے تحریری عملیات کو دوبارہ کوشش کے لیے محفوظ بنائیں، تاکہ ٹائم آؤٹ کے بعد دوبارہ کوشش کرنے والا کلائنٹ دو بار چارج یا دو بار تخلیق نہ کرے۔ ہر فہرست کے اینڈ پوائنٹ کی صفحہ بندی پہلے دن سے کریں، اور بڑے یا بدلتے ڈیٹا سیٹس کے لیے کرسر پر مبنی صفحہ بندی کو ترجیح دیں۔ شرح کی حدیں لاگو اور دستاویزی کریں، اور کلائنٹس کو موجودہ حد کی حالت واپس کریں تاکہ وہ شائستگی سے پیچھے ہٹ سکیں۔

### APIs کو منظم کریں اور ڈویلپر تجربے میں سرمایہ کاری کریں

ہر API کو پروڈکٹ سمجھیں، مالک، لائف سائیکل اور فہرست کے اندراج کے ساتھ۔ ڈیزائن ریویو یا API معیارات کا بورڈ قائم کریں تاکہ انٹرفیسز ٹیموں میں مستقل رہیں۔ ڈویلپر تجربے میں سرمایہ کاری کریں: درست حوالہ دستاویزات، فوری آغاز، مثالیں، سینڈ باکس، اور تبدیلی کا لاگ۔ بڑے ماحولیاتی نظام میں APIs کو قابل دریافت بنانے والا پورٹل یا فہرست ضروری ہے۔

## سمجھوتے: فوائد اور نقصانات

| اسلوب | کس کے لیے بہترین | فوائد | نقصانات |
|---|---|---|---|
| REST / HTTP | عوامی، وسائل پر مبنی APIs | ہر جگہ، کیش ہونے کے قابل، سادہ، قابل تعامل | ضرورت سے کم یا زیادہ حاصل کرنا؛ بہت سے چکر؛ تصریح کے بغیر ڈھیلے معاہدے |
| GraphQL | متنوع کلائنٹس کے لیے لچکدار پڑھت | کلائنٹ کی متعین کردہ استفسارات؛ ایک اینڈ پوائنٹ؛ مضبوط اسکیما | کیشنگ اور شرح کی حد کی پیچیدگی؛ استفسار کی لاگت کے خطرات؛ سرور کی پیچیدگی |
| gRPC | اندرونی اعلیٰ کارکردگی کی کالز | تیز، مختصر، مضبوط ٹائپ شدہ، اسٹریمنگ | براؤزر کی کمزور حمایت؛ کم انسانی پڑھنے کے قابل؛ بھاری ٹولنگ |
| ایونٹ پر مبنی | غیر ہم وقت، ڈھیلے جڑے ورک فلو | ڈھیلا جوڑ؛ قابل توسیع؛ لچکدار | سوچنا مشکل؛ حتمی مستقل مزاجی؛ آپریشنل پیچیدگی |

ورژننگ کی حکمت عملیاں استحکام کو دیکھ بھال کے مقابل تولتی ہیں۔ بہت سے پرانے ورژن سپورٹ کرنا صارفین کی حفاظت کرتا ہے، مگر یہ اس کوڈ کو کئی گنا بڑھاتا ہے جسے آپ کو برقرار رکھنا اور ٹیسٹ کرنا ہے۔ پسماندہ مطابقت آپ کی اپنی آزادی کو صارف کے استحکام کے لیے بدلتی ہے، جو وسیع طور پر استعمال ہونے والی API کے لیے عموماً درست سودا ہے۔ بڑی تصویر: خراب API فیصلے کی لاگت ہر صارف انٹرفیس کی پوری زندگی میں ادا کرتا ہے۔ اس لیے حد پر تقریباً کسی بھی جگہ سے زیادہ ڈیزائن کی محنت لگانا قابل قدر ہے۔

## اپنی ٹیم کے ساتھ بحث کے سوالات

1. **آپ تبدیلی کو پسماندہ مطابقت والی بمقابلہ توڑنے والی کیسے درجہ بند کرتے ہیں، اور کون سی خودکار جانچ ریلیز سے پہلے خاموش ٹوٹ پھوٹ پکڑتی ہے؟** یہ باب سخت لکیر کھینچتا ہے: اختیاری فیلڈز اور نئے اینڈ پوائنٹس شامل کرنا محفوظ ہے، جبکہ فیلڈز ہٹانا یا نام بدلنا، اقسام بدلنا، یا فیلڈ کے معنی کو دوبارہ مقصد دینا صارفین کو توڑتا ہے۔ بڑی ٹیم میں تبدیلی کرنے والا شخص اکثر ہر صارف کو نہیں دیکھ سکتا، اس لیے "چھوٹی" ترمیم خاموشی سے ان شراکت داروں کو توڑ سکتی ہے جن سے آپ کبھی بات نہیں کرتے۔ اجلاس میں ٹھوس اشارہ لائیں: کیا آپ شائع شدہ تصریح کے خلاف CI میں خودکار معاہدے کی مطابقت کی جانچیں چلاتے ہیں، یا کسی کے اصول یاد رکھنے پر انحصار کرتے ہیں۔ انٹرپرائز اور سرکاری ماحول میں، جہاں توڑنے والی تبدیلی ہر شراکت دار کے پار ہم آہنگ منتقلی مجبور کرتی ہے اور فروخت کنندہ اور انتظامیہ کی تبدیلیوں پر پھیل سکتی ہے، لاگت صارفین کی تعداد کے ساتھ بڑھتی ہے۔ درجہ بندی کے اصول طے کریں اور مطابقت کا دروازہ لگائیں، تاکہ غیر موافق تبدیلی انضمام کے بجائے بلڈ کو ناکام کرے۔

2. **کون سے اعتماد کے بنیادی اجزا، ایڈمپوٹنس کیز، صفحہ بندی اور شرح کی حد، ہر نئے اینڈ پوائنٹ پر پہلے دن سے لازمی ہیں؟** باب اصرار کرتا ہے کہ یہ اولین تشویشات ہیں، کیونکہ زندہ چارج اینڈ پوائنٹ پر ایڈمپوٹنس کی لگانا یا پہلے سے ریلیز شدہ فہرست میں صفحہ بندی شامل کرنا خود توڑنے والی تبدیلی ہے۔ بڑا ماحولیاتی نظام اسے بڑھاتا ہے: ٹیسٹنگ میں کام کرنے والا اینڈ پوائنٹ حقیقی ڈیٹا کی مقدار تلے ڈھ جاتا ہے، اور غیر ایڈمپوٹنٹ تحریر ایک نیٹ ورک کی ہچکی کو دوہری چارجز میں بدل دیتی ہے۔ شواہد لائیں کہ موجودہ اینڈ پوائنٹس میں سے کن میں یہ نہیں اور دوبارہ کوشش کا طوفان کیا کرے گا۔ نئے اینڈ پوائنٹس کے لیے ڈیفالٹس کو ناقابل مذاکرات بنائیں: ہر فہرست پر کرسر صفحہ بندی، ہر تحریر پر ایڈمپوٹنس کیز، دستاویزی شرح کی حدیں جو اپنی موجودہ حالت واپس کریں۔ یہ مستقبل کی مجبور منتقلی کو ایک بار کی ڈیزائن کی عادت میں بدل دیتا ہے۔

3. **کیا آپ واقعی نفاذ لکھنے سے پہلے معاہدہ ڈیزائن اور ریویو کرتے ہیں، یا انٹرفیس کوڈ سے ٹپکتا ہے؟** API-پہلے کی سفارش مشین سے پڑھی جانے والی تصریح مانگتی ہے، جس کا پہلے ریویو ہو، جو دستاویزات، اسٹبز اور نقلیں پیدا کرے اور صارفین کو آپ کے بناتے وقت نقلی کے خلاف انضمام کرنے دے۔ جب معاہدہ نفاذ سے پیچھے رہ جائے تو انٹرفیس اندرونی ڈیٹا بیس کی ساخت ظاہر کرتا ہے اور نفاذ کے بدلنے کے ساتھ بدلتا ہے، جو اس باب کا سب سے اوپر کا ضد نمونہ ہے۔ جس اشارے کو جانچنا ہے: کیا صارف آج آپ کی نقلی کے خلاف انضمام شروع کر سکتا ہے، یا اسے چلتے بیک اینڈ کا انتظار کرنا پڑتا ہے۔ عوامی اور شراکت داروں کی APIs کے لیے، جہاں انٹرفیس پروڈکٹ کی سطح ہے اور غلط کرنے کے لیے سب سے مہنگی چیز، معاہدے پر ایک دن لگانا مدد کے ہفتوں کی ہلچل بچاتا ہے۔ نفاذ شروع ہونے سے پہلے معاہدے کے ریویو کو لازمی قدم بنائیں۔

4. **جب دو ٹیموں کو ایک ہی صلاحیت ظاہر کرنی ہو تو کون سا تعامل کا انداز جیتتا ہے، اور چوتھے پروٹوکول کو انکار کرنے کا اختیار کس کو ہے؟** یہ باب آپ کو REST، GraphQL، gRPC یا ایونٹ پر مبنی پیغام رسانی تعامل کی موزونیت سے چننے کو کہتا ہے، مگر بڑے پیمانے پر اصل خطرہ یہ ہے کہ ہر ٹیم اپنا پسندیدہ چنتی ہے اور صارفین کو ہر اینڈ پوائنٹ پر مختلف اصول کا سامنا ہوتا ہے۔ بڑا ادارہ اس بکھراؤ کی قیمت کلائنٹ لائبریریوں، گیٹ ویز، مانیٹرنگ، اور ہر انضمام کرنے والے کے ذہنی بوجھ میں ادا کرتا ہے جو اب ایک کے بجائے چار محاورے سیکھتا ہے۔ پروڈکشن میں پہلے سے موجود پروٹوکولز کی فہرست لائیں، ہر ایک جس تعامل کے لیے چنا گیا، اور وہ صارفین جو ایک سے زیادہ پر محیط ہیں۔ متصادم غور حقیقی ہے: مشترک ڈیفالٹ پھیلاؤ کم کرتا ہے، پھر بھی سخت حکم gRPC کی شکل کے مسائل کو REST کی شکل کے سوراخ میں ٹھونس دیتا ہے۔ نام لیں کہ استثنا کے عمل کا مالک کون سا معیارات کا ادارہ یا فن تعمیر کا جائزہ ہے، کیونکہ انٹرپرائز اور سرکاری نظاموں میں اسلوبوں کا پھیلاؤ انضمام پر مستقل محصول اور الٹانا مشکل مسئلہ بن جاتا ہے جب شراکت دار ہر ایک پر انحصار کرنے لگیں۔

5. **ہماری شائع شدہ متروک کرنے کی پالیسی کیا ہے، اور کیا ہم ثابت کر سکتے ہیں کہ ہم اپنی بتائی ہوئی سپورٹ کی کھڑکی کا احترام کرتے ہیں؟** باب ورژننگ اور متروک کرنے کو نظم و ضبط سمجھتا ہے: پرانے ورژن کتنی دیر رہیں گے، صارفین کو کیسے اطلاع دی جائے گی، اور انہیں منتقل ہونے کے لیے کیا ملاپ ملے گا، اس کی تحریری پالیسی۔ جس وعدے کو آپ نافذ نہیں کر سکتے وہ بالکل نہ ہونے سے بدتر ہے، کیونکہ بڑے ماحولیاتی نظام میں وہ صارفین شامل ہیں جن سے آپ کبھی بات نہیں کرتے اور جو منسوخ شدہ ورژن کو اس وقت تک کال کرتے رہیں گے جب تک وہ پروڈکشن میں ٹوٹ نہ جائے۔ بحث میں شواہد لائیں: آج آپ کتنے زندہ ورژن اٹھا رہے ہیں، ہر ایک پر حقیقی استعمال، کیا آپ دیکھ سکتے ہیں کہ کون سے صارفین اب بھی متروک اینڈ پوائنٹ کو کال کرتے ہیں، اور آپ کا آخری غروب کتنا پہلے اعلان ہوا۔ متصادم دباؤ دیکھ بھال کی لاگت بمقابلہ صارف کا استحکام ہے، اور دونوں حقیقی ہیں۔ معاہداتی سروس کی سطحوں کے تحت انٹرپرائز شراکت داروں اور انتظامیہ اور فروخت کنندہ کی تبدیلیوں سے بچنے والی سرکاری شعبے کی APIs کے لیے سپورٹ کی کھڑکی وہ عہد ہے جو اسے کرنے والی ٹیم سے زیادہ جی سکتا ہے، اس لیے طے کریں کہ اس کا مالک کون ہے اور غروب سے پہلے کیسے ثابت ہو کہ وہ محفوظ ہے۔

6. **ہمیں کیسے معلوم کہ ہمارا ڈویلپر تجربہ اچھا ہے، یا ہم فرض کر رہے ہیں کیونکہ API ہمارے لیے کام کرتی ہے؟** یہ باب ہر API کو ایسی پروڈکٹ کے طور پر پیش کرتا ہے جس کا اپنایا جانا درست حوالہ دستاویزات، فوری آغاز، مثالوں، سینڈ باکس، تبدیلی کے لاگ، اور قابل دریافت فہرست پر منحصر ہے۔ ٹیمیں معمول کے مطابق "API کام کرتی ہے" کو "API قابل استعمال ہے" سمجھ لیتی ہیں، اور خلا سپورٹ ٹکٹوں، ناکام انضمام، اور ان صارفین کی صورت میں ظاہر ہوتا ہے جو خاموشی سے ہار مان جاتے ہیں۔ آراء کے بجائے قابل پیمائش اشارے لائیں: نئے انضمام کرنے والے کے لیے پہلی کامیاب کال تک کا وقت، فی اینڈ پوائنٹ سپورٹ ٹکٹوں کی مقدار، شائع شدہ دستاویزات زندہ معاہدے کے مقابل کتنی باسی ہیں، اور کیا نیا آنے والا آپ کی ٹیم کو ای میل کیے بغیر پورٹل سے خود سروس کر سکتا ہے۔ کھنچاؤ یہ ہے کہ دستاویزات اور پورٹلز میں حقیقی محنت لگتی ہے جو فیچرز ریلیز کرنے سے مقابلہ کرتی ہے، پھر بھی بڑے ماحولیاتی نظام میں ناقص ڈویلپر تجربہ ایک ساتھ سینکڑوں صارفین پر انضمام کی لاگت ڈال دیتا ہے۔ حکومت میں، جہاں کھلی API ایسے بیرونی ڈویلپرز کی خدمت کرتی ہے جن سے آپ ہم آہنگی نہیں کر سکتے اور شفافیت اکثر لازمی ہے، قابل استعمال، اچھی طرح دستاویزی، قابل دریافت انٹرفیس عوامی جوابدہی کی ذمہ داری کا حصہ ہے، اچھا ہونا کافی نہیں۔

## شعبہ جاتی نقطۂ نظر

**اسٹارٹ اپ۔** دو یا تین انجینئروں اور رسم کے لیے وقت نہ ہونے کے ساتھ معاہدے کو ہلکا مگر حقیقی رکھیں: ایک مشین سے پڑھی جانے والی تصریح جس کے خلاف آپ کے پہلے ڈیزائن شراکت دار صارفین آپ کے بناتے وقت انضمام کر سکیں۔ ابھی API گیٹ وے، فہرست، یا نظم و نسق کا بورڈ نہ بنائیں، لیکن دو عادتیں پکی کر لیں جن کا بعد میں جوڑنا تکلیف دہ ہے، تحریروں پر ایڈمپوٹنس کیز اور فہرستوں پر کرسر صفحہ بندی، کیونکہ زندہ اینڈ پوائنٹ پر انہیں بعد میں لگانا توڑنے والی تبدیلی ہے جو آپ برداشت نہیں کر سکتے۔ ایک تعامل کا انداز، تقریباً ہمیشہ REST، ترجیح دیں تاکہ آپ پہلے سال میں پروٹوکول کا پھیلاؤ نہ اٹھائیں۔

**چھوٹا کاروبار۔** کوئی مخصوص API ماہر اور تنگ بجٹ نہ ہونے کی صورت میں ان ٹولز پر انحصار کریں جو تصریح سے دستاویزات، نقلیں اور کلائنٹ اسٹبز بناتے ہیں تاکہ ماہر عمومی شخص گہری پروٹوکول مہارت کے بغیر انٹرفیس برقرار رکھ سکے۔ خریدنے اور بنانے کو سختی سے تولیں: تیار شدہ گیٹ وے یا API مینجمنٹ پلیٹ فارم آپ کو شرح کی حد، کیز، اور ڈویلپر پورٹل دیتا ہے جو آپ ورنہ ہاتھ سے بناتے۔ سطح چھوٹی اور اصول مستقل رکھیں، کیونکہ ہر اضافی اینڈ پوائنٹ اور ہر ایک بار کا خرابی کا فارمیٹ وہ چیز ہے جسے پتلی ٹیم کو ہمیشہ سپورٹ کرنا پڑے گا۔

**بڑا ادارہ۔** بہت سی خود مختار ٹیموں میں مرکزی مسئلہ رکاوٹ بنے بغیر یکسانیت ہے: مشترک اسلوب گائیڈ، API معیارات کا ریویو، انٹرفیسز کو قابل دریافت بنانے والی فہرست، اور CI میں خودکار پسماندہ مطابقت کی جانچیں تاکہ خاموش ٹوٹ پھوٹ انضمام کے بجائے بلڈ کو ناکام کرے۔ ہر API کو نام زد مالک، لائف سائیکل اور شائع شدہ متروک کرنے کی پالیسی کے ساتھ پروڈکٹ کی طرح منظم کریں، اور اپنانے، سپورٹ کے بوجھ اور توڑنے والی تبدیلی کی تعدد ناپیں تاکہ پورٹ فولیو صحت مند رہے۔ تعامل کے اسلوب اور ورژننگ کے اصولوں کو پورے ادارے میں معیاری بنائیں، کیونکہ اس پیمانے پر بکھراؤ مہنگا ڈیفالٹ ہے۔

**حکومت۔** خریداری کے قواعد، کھلے معیارات کے احکامات، اور عوامی جوابدہی ہر انتخاب کو شکل دیتے ہیں۔ معاہدہ کھلے عام شائع کریں، لازمی کھلے معیارات کی پیروی کریں، اور سینڈ باکس اور حوالہ دستاویزات فراہم کریں تاکہ بیرونی ڈویلپرز جن سے آپ ہم آہنگی نہیں کر سکتے خود سروس کر سکیں۔ طویل مدتی پسماندہ مطابقت کو پالیسی کا تقاضا سمجھیں، کیونکہ انضمام کو انتظامیہ اور فروخت کنندہ کی تبدیلیوں میں بچنا ہوتا ہے، اور توڑنے والی تبدیلیاں نایاب، بھاری طور پر منظم، اور بہت پہلے اعلان شدہ بنائیں۔ API اور اس کی دستاویزات کو عوامی اور آڈٹ جانچ برداشت کرنے کے لیے کافی شفاف رکھیں، اور ایسے ملکیتی فارمیٹ سے بچیں جو آئندہ انتظامیہ کو پھنسا دے۔

## مثالیں

**اسٹارٹ اپ۔** اپنی پہلی عوامی API ریلیز کرنے والا ابتدائی مرحلے کا اسٹارٹ اپ کوڈنگ سے پہلے معاہدہ مشین سے پڑھی جانے والی تصریح کے طور پر لکھتا ہے، تاکہ اس کے دو ڈیزائن شراکت دار صارفین بیک اینڈ بنتے وقت نقلی کے خلاف انضمام کر سکیں۔ حتیٰ کہ چند صارفین کے ساتھ بھی وہ چارج اینڈ پوائنٹ میں ایڈمپوٹنس کیز اور ہر فہرست میں کرسر صفحہ بندی شامل کرتا ہے، کیونکہ شراکت داروں کے API پر انحصار کے بعد انہیں بعد میں لگانا ایسی توڑنے والی تبدیلی ہوگی جو وہ برداشت نہیں کر سکتا۔ آگے کا معاہدہ ایک دن لیتا ہے اور سپورٹ کی ہفتوں کی آمد و رفت بچاتا ہے۔

**بڑا ادارہ۔** ایک بڑی ادائیگیوں کی کمپنی ہزاروں تاجروں کے لیے عوامی REST API پیش کرتی ہے۔ ہر تحریری اینڈ پوائنٹ ایڈمپوٹنس کی قبول کرتا ہے، اس لیے نیٹ ورک کی دوبارہ کوشش کبھی دوہرا چارج نہیں بناتی۔ ہر فہرست کا اینڈ پوائنٹ کرسر صفحہ بندی استعمال کرتا ہے۔ خرابیاں مستحکم کوڈ رکھتی ہیں جو عوامی حوالے میں دستاویزی ہیں۔ باضابطہ متروک کرنے کی پالیسی کسی بھی ورژن کے لیے پیشگی اطلاع اور منتقلی کی گائیڈز کے ساتھ لمبی سپورٹ کی کھڑکی کی ضمانت دیتی ہے۔ یہ نظم و ضبط مسابقتی فائدہ ہے: انضمام کرنے والے اعتماد کرتے ہیں کہ API ان کے نیچے نہیں ٹوٹے گی۔

**حکومت۔** ایک قومی ڈیجیٹل سروس شہری ڈیٹا کے لیے کھلی API شائع کرتی ہے، لازمی کھلے معیارات اور API-پہلے ڈیزائن کے عمل کی پیروی کرتے ہوئے۔ معاہدہ تعمیر سے پہلے متعین اور ریویو ہوتا ہے، مرکزی سرکاری API فہرست میں شائع ہوتا ہے، اور سینڈ باکس کے ساتھ پیش ہوتا ہے، تاکہ تیسرے فریق کے ڈویلپرز، جن سے انفرادی طور پر ہم آہنگی نہیں ہو سکتی، خود انضمام کر سکیں۔ طویل مدتی پسماندہ مطابقت پالیسی کا تقاضا ہے، کیونکہ انضمام کو انتظامیہ اور فروخت کنندہ کی تبدیلیوں میں بچنا ہوتا ہے۔ اس لیے توڑنے والی تبدیلیاں نایاب اور بھاری طور پر منظم ہیں۔

## کاروباری جواز: محرکات، ROI اور TCO

اچھا API ڈیزائن انضمام کی لاگت کم کرتا ہے، جو نظاموں کو جوڑنے اور شراکت داروں کو آغاز کار کرانے میں اکثر سب سے بڑی لاگت ہوتی ہے۔ واضح، مستحکم، اچھی طرح دستاویزی API کے ساتھ صارفین ایک بھی سپورٹ ٹکٹ کے بغیر دنوں میں انضمام کر لیتے ہیں۔ خراب API لامتناہی سپورٹ کا بوجھ، ناکام انضمام اور ساکھ کا نقصان پیدا کرتی ہے۔ جب API خود پروڈکٹ ہو تو ڈویلپر تجربہ براہ راست اپنانے اور آمدنی کو چلاتا ہے۔

سب سے بڑی چھپی لاگت توڑنے والی تبدیلیاں ہیں۔ ہر توڑنے والی تبدیلی تمام صارفین، اندرونی ٹیموں اور بیرونی شراکت داروں، کے پار ہم آہنگ منتقلی پر مجبور کرتی ہے، اور کل لاگت صارفین کی تعداد اور ان کے لیے ہم قدم منتقل ہونے کی مشکل کے ساتھ بڑھتی ہے۔ معاہدے پر مبنی ڈیزائن، پسماندہ مطابقت اور ورژننگ کے نظم و ضبط میں آگے سرمایہ کاری ان مہنگے، ادارے بھر کے منتقلی کے واقعات سے بچاتی ہے۔ جب آپ قیادت سے بات کریں تو API کے معیار کو ٹیم کی خود مختاری، شراکت داروں کے ماحولیاتی نظام کی ترقی، اور مہنگی مجبور منتقلیوں سے بچنے کا لیور پوائنٹ بنا کر پیش کریں۔ انضمام کا وقت، سپورٹ ٹکٹوں کی مقدار، اور توڑنے والی تبدیلی کی تعدد کو اپنے شواہد کے طور پر ٹریک کریں۔

## ضد نمونے اور خامیاں

- **نفاذ-پہلے APIs:** انٹرفیس اندرونی ڈیٹا بیس کی ساخت ظاہر کرتا ہے اور نفاذ کے بدلنے کے ساتھ بدلتا ہے۔
- **خاموش توڑنے والی تبدیلیاں:** فیلڈ کو دوبارہ مقصد دینا یا ورژن بڑھائے بغیر توثیق سخت کرنا صارفین کو غیر متوقع طور پر توڑتا ہے۔
- **باتونی انٹرفیسز:** ایسے ڈیزائن جو ایک منطقی عمل کے لیے بہت سے چکر مانگتے ہیں، کارکردگی اور قابل استعمال ہونے کو نقصان پہنچاتے ہیں۔
- **غیر مستقل اصول:** ہر اینڈ پوائنٹ اپنا نام رکھنا، خرابی کا فارمیٹ اور صفحہ بندی ایجاد کرتا ہے، اس لیے کلائنٹس عمومیت نہیں کر سکتے۔
- **صفحہ بندی یا شرح کی حد نہیں:** اینڈ پوائنٹس جو ٹیسٹنگ میں کام کرتے ہیں اور حقیقی ڈیٹا کی مقدار یا بوجھ تلے ڈھ جاتے ہیں۔
- **غیر ایڈمپوٹنٹ تحریریں:** دوبارہ کوششیں نقلیں بناتی ہیں؛ ایک نیٹ ورک کی ہچکی ڈیٹا بگاڑ دیتی ہے۔
- **ورژنوں کا پھیلاؤ:** بہت سے زندہ ورژن جن کو متروک نہیں کیا جاتا، دیکھ بھال کو اس حد تک بڑھاتے ہیں کہ سنبھالنا ناممکن ہو۔
- **بعد کے خیال کے طور پر دستاویزات:** غیر دستاویزی یا پرانے حوالے جو انضمام کی ساری لاگت صارفین پر دھکیل دیتے ہیں۔

## پختگی کا ماڈل

- **سطح 1، آغاز:** APIs نفاذ سے ضمنی پیداوار کے طور پر ابھرتی ہیں؛ کوئی مشترک اصول نہیں؛ انٹرفیس اندرونی ڈیٹا بیس کی ساخت ظاہر کرتا ہے؛ توڑنے والی تبدیلیاں عام، غیر اعلان شدہ ہیں اور صارف کے انضمام کے ناکام ہونے پر دریافت ہوتی ہیں۔
- **سطح 2، ترقی:** کچھ ٹیمیں بنیادی REST اصولوں کی پیروی کرتی ہیں، غیر رسمی ورژن بناتی ہیں، اور دستاویزات ہاتھ سے لکھتی ہیں، مگر عمل ٹیموں میں غیر مستقل ہے؛ ایڈمپوٹنس، صفحہ بندی اور شرح کی حد کچھ اینڈ پوائنٹس پر ہیں اور کچھ پر نہیں؛ صارفین اب بھی ہر API کی خصوصیات کیس بہ کیس سیکھتے ہیں۔
- **سطح 3، معیار بندی:** مشین سے پڑھی جانے والی تصریحات کے ساتھ معاہدے پر مبنی ڈیزائن دستاویزی اور پورے ادارے میں نافذ ہے؛ شائع شدہ متروک کرنے کی پالیسی، مستقل خرابی کے معنی، اور لازمی ایڈمپوٹنس، کرسر صفحہ بندی اور شرح کی حد ہر نئے اینڈ پوائنٹ پر لاگو ہیں؛ مشترک اسلوب گائیڈ اور API معیارات کا ریویو ٹیموں میں انٹرفیسز کو مستقل رکھتے ہیں۔
- **سطح 4، انتظام:** API پورٹ فولیو کو بنیادی خطوط کے مقابل ناپا اور کنٹرول کیا جاتا ہے: خودکار پسماندہ مطابقت کی جانچیں CI میں ہر تبدیلی کا دروازہ ہیں، اور آپ پہلی کامیاب کال تک کا وقت، فی اینڈ پوائنٹ سپورٹ ٹکٹوں کی مقدار، توڑنے والی تبدیلی کی تعدد، زندہ ورژنوں کی تعداد، اور فی اینڈ پوائنٹ استعمال ٹریک کرتے ہیں تاکہ متروک کرنے اور ڈیزائن کے فیصلے رائے کے بجائے شواہد پر ٹکیں۔ ہر API نام زد مالک کے ساتھ فہرست میں منظم پروڈکٹ ہے، اور جب سروس اپنے اہداف سے بھٹکے تو اشاریے عمل متحرک کرتے ہیں۔
- **سطح 5، ہم آہنگی:** API کی حکمت عملی مسلسل بہتر اور پورے ادارے میں مربوط ہے؛ فہرست، گیٹ وے، ورژننگ کے اصول اور مطابقت کے دروازے ایک نظام کے طور پر کام کرتے ہیں؛ ادارہ ناپے گئے اپنانے اور لاگت کی بنیاد پر معمول کے مطابق انٹرفیسز ریٹائر، مجتمع اور دوبارہ دائرہ بند کرتا ہے؛ تعامل کے اسلوب اور ورژننگ کے معیارات ماحولیاتی نظام، شراکت داروں اور ٹیکنالوجی کے بدلنے کے ساتھ ڈھلتے ہیں، اور توڑنے والی تبدیلیاں نایاب اور اچھی طرح سنبھالی جاتی ہیں۔

## بحث کے لیے خیالات

- آپ کیسے طے کرتے ہیں کہ اندرونی API بیرونی طور پر شائع کرنے کے لیے کب کافی مستحکم ہے؟
- آپ کے سیاق میں متروک ورژنوں کے لیے سپورٹ کی درست کھڑکی کیا ہے، اور اس کی ادائیگی کون کرتا ہے؟
- اندرونی طور پر GraphQL یا gRPC کو REST کی جگہ کہاں لینی چاہیے، اور کہاں وہ قدر سے زیادہ پیچیدگی جوڑیں گے؟
- آپ رکاوٹ بنے بغیر بہت سی خود مختار ٹیموں میں API کی یکسانیت کیسے نافذ کرتے ہیں؟
- AI کے استعمال کے قابل APIs اور ایجنٹ ٹول انٹرفیسز کو آپ کے ڈیزائن کے اصولوں کو کیسے بدلنا چاہیے؟
- کون سی خودکار جانچیں پسماندہ طور پر غیر موافق تبدیلیوں کو ریلیز سے پہلے پکڑ سکتی ہیں؟

## اہم نکات

- پہلے معاہدہ ڈیزائن کریں؛ API پروڈکٹ اور طویل العمر وعدہ ہے۔
- پسماندہ مطابقت صارفین کی حفاظت کرتی ہے؛ توڑنے والی تبدیلیوں کو نئے ورژن اور منتقلی کے راستے چاہئیں۔
- REST، GraphQL، gRPC یا ایونٹس تعامل کی موزونیت سے چنیں، فیشن سے نہیں۔
- ایڈمپوٹنس، صفحہ بندی، شرح کی حد اور مستقل خرابیاں پہلے دن سے شامل کریں۔
- APIs کو مالکوں، فہرستوں اور مضبوط ڈویلپر تجربے کے ساتھ مصنوعات کی طرح منظم کریں۔
