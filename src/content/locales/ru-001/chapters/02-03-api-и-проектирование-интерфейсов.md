# 2.3 API и проектирование интерфейсов

## Обзор и мотивация

[API](https://en.wikipedia.org/wiki/API) (программный интерфейс приложения) это контракт, через который одна программа предлагает возможность другой. Это место, где встречаются команды, системы и организации, и это самое долговечное и дорогое, в чём можно ошибиться. Вы можете свободно рефакторить сигнатуру внутренней функции. Опубликованный API другое дело: это обещание потребителям, которых вы можете никогда не встретить, и его нарушение ломает их. По мере того как организации разбивают [монолиты](https://en.wikipedia.org/wiki/Monolithic_application) на сервисы и открывают возможности партнёрам и публике, API становится главной поверхностью продукта и главным интеграционным риском.

Для больших команд API это то, что позволяет людям работать независимо. Хорошо спроектированный интерфейс позволяет менять нутро без согласования с каждым потребителем, в чём и состоит весь смысл границы сервиса. Плохо спроектированный раскрывает внутренние детали, вынуждает к согласованному развёртыванию и превращает набор сервисов в распределённый монолит: сервисы разделены, но так сцеплены, что их нужно строить и развёртывать вместе. Проектирование вашего API напрямую определяет, насколько независимо могут двигаться ваши команды.

В корпоративной и государственной среде API также несут обязательства по соответствию, безопасности и долговечности. От государственного API может требоваться следование [открытым стандартам](https://en.wikipedia.org/wiki/Open_standard), стабильность на годы и обслуживание внешних разработчиков, с которыми нельзя координироваться. Корпоративные API лежат в основе партнёрских интеграций с контрактными уровнями обслуживания. Всё это поднимает планку дисциплины версионирования, [обратной совместимости](https://en.wikipedia.org/wiki/Backward_compatibility), управления и опыта разработчика.

## Ключевые принципы

- Проектируйте контракт первым. Интерфейс это намеренное продуктовое решение, а не побочный продукт реализации.
- Оптимизируйте опыт потребителя, а не собственное удобство.
- Рассматривайте обратную совместимость как обещание. Ломающие изменения требуют новой версии и пути миграции.
- Делайте простое правильным: разумные значения по умолчанию, предсказуемые ошибки, единые соглашения.
- Проектируйте с расчётом на отказ. [Идемпотентность](https://en.wikipedia.org/wiki/Idempotence) (повторный запрос имеет тот же эффект, что и единичный), повторы, пагинация и [ограничение частоты запросов](https://en.wikipedia.org/wiki/Rate_limiting) первоклассные заботы, а не запоздалые мысли.
- Выбирайте стиль протокола под взаимодействие, а не под моду.
- Управляйте API как продуктами, с владельцами, жизненными циклами и документацией.

## Рекомендации

### Работайте сначала с API и ведите разработку от контракта

Определите и рассмотрите контракт API, включая его ресурсы, операции, схемы и семантику ошибок, до написания реализации. Используйте машиночитаемую спецификацию, чтобы контракт мог порождать документацию, заглушки клиента и сервера, имитационные серверы и валидацию. Тогда потребители могут начать интеграцию с имитацией, пока вы строите, а контракт становится единым источником истины, против которого тестируют обе стороны.

### Выбирайте стиль взаимодействия намеренно

Выбирайте между [REST](https://en.wikipedia.org/wiki/REST) (передача состояния представления), [GraphQL](https://en.wikipedia.org/wiki/GraphQL), [gRPC](https://en.wikipedia.org/wiki/GRPC) и [событийным обменом сообщениями](https://en.wikipedia.org/wiki/Event-driven_architecture) по характеру взаимодействия, а не по личному предпочтению. Используйте REST для ресурсно-ориентированных, широко совместимых, кэшируемых интерфейсов. Используйте GraphQL, когда разнообразным клиентам нужны гибкие агрегированные чтения по богатому графу. Используйте gRPC для высокопроизводительных строго типизированных вызовов между внутренними сервисами. Используйте событийный обмен сообщениями для асинхронных, слабосвязанных рабочих процессов и распространения изменений состояния. Многие большие системы используют несколько стилей одновременно, каждый там, где он подходит.

### Версионируйте и выводите из обращения дисциплинированно

Примите явную стратегию версионирования и опубликованную политику вывода из обращения: как вы классифицируете изменения, как долго поддерживаете старые версии и как уведомляете потребителей. Проведите чёткую черту между обратно совместимыми изменениями (добавление необязательных полей, новые конечные точки) и ломающими (удаление или переименование полей, смена типов или семантики). Никогда не переопределяйте смысл существующего поля. Давайте потребителям окна перекрытия для миграции и сообщайте сроки заблаговременно.

### Делайте семантику ошибок единой и машиночитаемой

Возвращайте структурированные, предсказуемые ошибки: стабильные машиночитаемые коды, человекочитаемые сообщения и достаточно контекста для действия, не раскрывая чувствительных внутренностей. Используйте одну семантику статусов во всех конечных точках, чтобы клиенты могли обрабатывать ошибки единообразно. Документируйте каждую ошибку, с которой может столкнуться потребитель.

### Встройте идемпотентность, пагинацию и ограничение частоты

Делайте операции записи безопасными для повтора, поддерживая ключи идемпотентности, чтобы клиент, повторяющий запрос после тайм-аута, не списывал деньги дважды и не создавал дубликатов. Разбивайте на страницы каждую конечную точку списка с первого дня и предпочитайте пагинацию на основе курсора для больших или изменяющихся наборов данных. Применяйте и документируйте ограничения частоты и возвращайте клиентам текущее состояние лимита, чтобы они могли изящно отступать.

### Управляйте API и вкладывайтесь в опыт разработчика

Воспринимайте каждый API как продукт с владельцем, жизненным циклом и записью в каталоге. Организуйте ревью проектов или совет по стандартам API, чтобы интерфейсы оставались согласованными между командами. Вкладывайтесь в опыт разработчика: точную справочную документацию, краткие руководства, примеры, песочницу и журнал изменений. В большой экосистеме портал или каталог, делающий API находимыми, необходим.

## Компромиссы: плюсы и минусы

| Стиль | Лучше всего для | Плюсы | Минусы |
|---|---|---|---|
| REST / HTTP | Публичных ресурсно-ориентированных API | Повсеместность, кэшируемость, простота, совместимость | Избыточная и недостаточная выборка; много обращений; слабые контракты без спецификации |
| GraphQL | Гибких чтений для разных клиентов | Запросы, задаваемые клиентом; одна конечная точка; сильная схема | Сложность кэширования и ограничения частоты; риски стоимости запросов; сложность сервера |
| gRPC | Внутренних высокопроизводительных вызовов | Быстрый, компактный, строго типизированный, потоковый | Слабая поддержка в браузерах; менее читаем человеком; более тяжёлые инструменты |
| Событийный | Асинхронных слабосвязанных рабочих процессов | Слабое сцепление; масштабируемость; устойчивость | Труднее рассуждать; согласованность в конечном счёте; операционная сложность |

Стратегии версионирования меняют стабильность на сопровождение. Поддержка многих старых версий защищает потребителей, но умножает код, который нужно поддерживать и тестировать. Обратная совместимость меняет вашу свободу на стабильность потребителей, обычно верный размен для широко используемого API. Общая картина: стоимость плохого решения по API платится каждым потребителем на всём протяжении жизни интерфейса. Поэтому стоит тратить больше усилий на проектирование на границе, чем почти где-либо ещё.

## Вопросы для обсуждения с командой

1. **Как вы классифицируете изменение как обратно совместимое или ломающее и какая автоматическая проверка ловит молчаливый слом до выпуска?** Эта глава проводит жёсткую черту: добавление необязательных полей и новых конечных точек безопасно, а удаление или переименование полей, смена типов или переопределение смысла поля ломает потребителей. В большой команде тот, кто вносит изменение, часто не видит всех потребителей, поэтому «небольшая» правка может тихо сломать партнёров, с которыми вы никогда не говорите. Принесите на встречу конкретный сигнал: запускаете ли вы автоматические проверки совместимости контракта в CI относительно опубликованной спецификации или полагаетесь на то, что кто-то вспомнит правило. В корпоративной и государственной среде, где ломающее изменение вынуждает к согласованной миграции у каждого партнёра и может охватывать смену поставщиков и администраций, стоимость растёт с числом потребителей. Решите правила классификации и подключите шлюз совместимости, чтобы несовместимое изменение валило сборку, а не интеграцию.

2. **Какие примитивы надёжности (ключи идемпотентности, пагинация и ограничение частоты) обязательны для каждой новой конечной точки с первого дня?** Глава настаивает, что это первоклассные заботы, потому что добавление ключа идемпотентности в живую конечную точку списания или пагинации в уже работающий список само ломающее изменение. Большая экосистема усиливает это: конечная точка, работающая при тестировании, рушится под реальным объёмом данных, а неидемпотентная запись превращает один сетевой сбой в двойные списания. Принесите свидетельства, у каких текущих конечных точек этого нет и что сделала бы лавина повторов. Сделайте умолчания обязательными для новых конечных точек: пагинация по курсору в каждом списке, ключи идемпотентности на каждой записи, документированные ограничения частоты, возвращающие своё текущее состояние. Это превращает будущую вынужденную миграцию в разовую проектную привычку.

3. **Вы действительно проектируете и рецензируете контракт до написания реализации или интерфейс вытекает из кода?** Рекомендация «сначала API» просит машиночитаемую спецификацию, рассмотренную заранее, порождающую документацию, заглушки и имитации и позволяющую потребителям интегрироваться с имитацией, пока вы строите. Когда контракт отстаёт от реализации, интерфейс раскрывает внутреннюю структуру базы данных и сдвигается каждый раз, когда сдвигается реализация, что главный антипаттерн этой главы. Сигнал для проверки: может ли потребитель начать интегрироваться с вашей имитацией сегодня или должен ждать работающий бэкенд. Для публичных и партнёрских API, где интерфейс поверхность продукта и самое дорогое, в чём можно ошибиться, день на контракт экономит недели возни с поддержкой. Сделайте ревью контракта обязательным шагом до начала реализации.

4. **Когда двум командам нужно открыть одну и ту же возможность, какой стиль взаимодействия побеждает и у кого есть полномочие сказать «нет» четвёртому протоколу?** Эта глава велит выбирать REST, GraphQL, gRPC или событийный обмен сообщениями по соответствию взаимодействию, но в масштабе настоящий риск в том, что каждая команда выбирает свой любимый, а потребители сталкиваются с другим соглашением на каждой конечной точке. Большая организация платит за эту фрагментацию клиентскими библиотеками, шлюзами, мониторингом и когнитивной нагрузкой на каждого интегратора, который теперь изучает четыре идиомы вместо одной. Принесите опись протоколов, уже работающих в эксплуатации, взаимодействие, для которого выбран каждый, и потребителей, использующих больше одного. Противоположное соображение подлинное: общее умолчание сокращает расползание, но жёсткий мандат загоняет задачи формы gRPC в отверстие формы REST. Назовите орган по стандартам или ревью архитектуры, владеющий процессом исключений, потому что в корпоративных и государственных ландшафтах размножение стилей становится постоянным налогом на интеграцию и трудно обратимо, когда от каждого зависят партнёры.

5. **Какова наша опубликованная политика вывода из обращения и можем ли мы доказать, что действительно соблюдаем заявленное окно поддержки?** Глава рассматривает версионирование и вывод из обращения как дисциплину: письменная политика о том, как долго живут старые версии, как уведомляются потребители и какое перекрытие они получают для миграции. Обещание, которое вы не можете обеспечить, хуже его отсутствия, потому что в большой экосистеме есть потребители, с которыми вы не говорите и которые продолжат вызывать выведенную версию, пока она не сломается в эксплуатации. Принесите свидетельства: сколько живых версий вы несёте сегодня, реальное использование каждой, можете ли вы видеть, какие потребители ещё вызывают устаревшую конечную точку, и насколько заранее объявлялся ваш последний вывод. Противоположное давление это стоимость сопровождения против стабильности потребителей, и оба реальны. Для корпоративных партнёров по контрактным уровням обслуживания и государственных API, которые должны пережить смену администраций и поставщиков, окно поддержки обязательство, которое может пережить команду, его принявшую, поэтому решите, кто им владеет и как доказывается безопасность вывода до того, как он произойдёт.

6. **Как мы знаем, что наш опыт разработчика хорош, или мы предполагаем это, потому что API работает для нас?** Эта глава рассматривает каждый API как продукт, принятие которого зависит от точной справочной документации, кратких руководств, примеров, песочницы, журнала изменений и находимого каталога. Команды регулярно принимают «API функционирует» за «API пригоден к использованию», и разрыв проявляется как обращения в поддержку, неудавшиеся интеграции и потребители, тихо сдающиеся. Принесите измеримые сигналы вместо мнений: время до первого успешного вызова для нового интегратора, объём обращений в поддержку по конечной точке, насколько устарела опубликованная документация относительно живого контракта и может ли новичок самообслуживаться с портала, не пиша вашей команде. Напряжение в том, что документация и порталы стоят реальных усилий, конкурирующих с выпуском функций, но в большой экосистеме плохой опыт разработчика перекладывает стоимость интеграции сразу на сотни потребителей. В государстве, где открытый API обслуживает внешних разработчиков, с которыми нельзя координироваться, а прозрачность часто предписана, пригодный, хорошо документированный, находимый интерфейс часть обязанности публичной подотчётности, а не приятное дополнение.

## Взгляд по секторам

**Стартап.** С двумя-тремя инженерами и без времени на церемонии держите контракт лёгким, но настоящим: одна машиночитаемая спецификация, с которой ваши первые клиенты-партнёры по проектированию могут интегрироваться, пока вы строите. Пока не поднимайте шлюз API, каталог или совет по управлению, но закрепите две привычки, которые больно добавлять позже: ключи идемпотентности на записях и пагинацию по курсору на списках, потому что их добавление в живую конечную точку ломающее изменение, которого вы не можете себе позволить. Предпочитайте один стиль взаимодействия, почти всегда REST, чтобы не нести расползание протоколов в первый год.

**Малый бизнес.** Без выделенного специалиста по API и при ограниченном бюджете опирайтесь на инструменты, порождающие документацию, имитации и заглушки клиентов из спецификации, чтобы универсал мог поддерживать интерфейс без глубокой экспертизы по протоколам. Взвешивайте «купить или построить» жёстко: готовый шлюз или платформа управления API даёт ограничение частоты, ключи и портал разработчика, которые иначе пришлось бы делать вручную. Держите поверхность малой, а соглашения единообразными, поскольку каждая лишняя конечная точка и каждый разовый формат ошибок это то, что тонкая команда должна поддерживать вечно.

**Крупная организация.** Между многими автономными командами центральная проблема в согласованности без превращения в узкое место: общее руководство по стилю, ревью стандартов API, каталог, делающий интерфейсы находимыми, и автоматические проверки обратной совместимости в CI, чтобы молчаливый слом валил сборку, а не интеграцию. Управляйте каждым API как продуктом с названным владельцем, жизненным циклом и опубликованной политикой вывода из обращения и измеряйте принятие, нагрузку на поддержку и частоту ломающих изменений, чтобы портфель оставался здоровым. Стандартизируйте стили взаимодействия и правила версионирования по всей организации, потому что в таком масштабе фрагментация дорогое умолчание.

**Государственный сектор.** Правила закупок, мандаты открытых стандартов и публичная подотчётность определяют каждый выбор. Публикуйте контракт открыто, следуйте предписанным открытым стандартам и предоставляйте песочницу и справочную документацию, чтобы внешние разработчики, с которыми нельзя координироваться, могли самообслуживаться. Рассматривайте долгосрочную обратную совместимость как требование политики, поскольку интеграции должны пережить смену администраций и поставщиков, и делайте ломающие изменения редкими, строго управляемыми и объявляемыми заблаговременно. Держите API и его документацию достаточно прозрачными, чтобы выдержать общественный и аудиторский контроль, и избегайте проприетарных форматов, которые заперли бы будущую администрацию.

## Примеры

**Стартап.** Стартап начальной стадии, выпускающий первый публичный API, пишет контракт как машиночитаемую спецификацию до кодирования, чтобы два клиента-партнёра по проектированию могли интегрироваться с имитацией, пока бэкенд ещё строится. Даже при горстке потребителей он добавляет ключи идемпотентности в конечную точку списания и пагинацию по курсору в каждый список, потому что добавление их, когда от API зависят партнёры, означало бы ломающее изменение, которое он не может себе позволить. Предварительный контракт стоит день и экономит недели переписки с поддержкой.

**Крупная организация.** Крупная платёжная компания открывает публичный REST API тысячам торговцев. Каждая конечная точка записи принимает ключ идемпотентности, так что сетевой повтор никогда не создаёт двойного списания. Каждая конечная точка списка использует пагинацию по курсору. Ошибки несут стабильные коды, документированные в публичном справочнике. Формальная политика вывода из обращения гарантирует длинное окно поддержки любой версии с заблаговременным уведомлением и руководствами по миграции. Эта дисциплина конкурентное преимущество: интеграторы доверяют, что API не сломается под ними.

**Государственный сектор.** Национальная цифровая служба публикует открытый API для данных граждан, следуя предписанным открытым стандартам и процессу проектирования «сначала API». Контракт описан и рассмотрен до построения, опубликован в центральном государственном каталоге API и обслуживается с песочницей, так что сторонние разработчики, с которыми нельзя координироваться по отдельности, могут интегрироваться самостоятельно. Долгосрочная обратная совместимость требование политики, поскольку интеграции должны пережить смену администраций и поставщиков. Поэтому ломающие изменения редки и строго управляемы.

## Бизнес-обоснование: мотивы, ROI и TCO

Хороший проект API снижает стоимость интеграции, часто крупнейшую статью затрат на связывание систем и подключение партнёров. С ясным, стабильным, хорошо документированным API потребители интегрируются за дни без единого обращения в поддержку. Плохой порождает бесконечную нагрузку на поддержку, неудавшиеся интеграции и репутационный ущерб. Когда API сам продукт, опыт разработчика напрямую определяет принятие и выручку.

Самая большая скрытая стоимость ломающие изменения. Каждое ломающее изменение вынуждает к согласованной миграции у всех потребителей, и внутренних команд, и внешних партнёров, а общая стоимость растёт с числом потребителей и трудностью для них двигаться согласованно. Предварительные вложения в проектирование от контракта, обратную совместимость и дисциплину версионирования позволяют избежать этих дорогих организационных событий миграции. Говоря с руководством, подавайте качество API как точку приложения рычага для автономии команд, роста партнёрской экосистемы и избегания дорогих вынужденных миграций. Отслеживайте время интеграции, объём обращений в поддержку и частоту ломающих изменений как свидетельства.

## Антипаттерны и ловушки

- **API, определяемые реализацией:** интерфейс раскрывает внутреннюю структуру базы данных и меняется каждый раз, когда меняется реализация.
- **Молчаливые ломающие изменения:** переопределение поля или ужесточение валидации без повышения версии непредсказуемо ломает потребителей.
- **Болтливые интерфейсы:** проекты, требующие многих обращений для одной логической операции, вредящие производительности и удобству.
- **Несогласованные соглашения:** каждая конечная точка изобретает своё именование, формат ошибок и пагинацию, поэтому клиенты не могут обобщать.
- **Нет пагинации и ограничения частоты:** конечные точки, работающие при тестировании и рушащиеся под реальным объёмом данных или нагрузкой.
- **Неидемпотентные записи:** повторы вызывают дубликаты; один сетевой сбой портит данные.
- **Размножение версий:** слишком много живых версий без вывода из обращения, умножающих сопровождение до неуправляемости.
- **Документация как запоздалая мысль:** недокументированные или устаревшие справочники, перекладывающие всю стоимость интеграции на потребителей.

## Модель зрелости

- **Уровень 1, Начальный:** API возникают из реализации как побочный продукт; общих соглашений нет; интерфейс раскрывает внутреннюю структуру базы данных; ломающие изменения часты, не объявлены и обнаруживаются, когда интеграция потребителя падает.
- **Уровень 2, Развитие:** Некоторые команды следуют базовым соглашениям REST, версионируют неформально и пишут документацию вручную, но практика непоследовательна между командами; идемпотентность, пагинация и ограничение частоты есть на одних конечных точках и нет на других; потребители по-прежнему изучают причуды каждого API по отдельности.
- **Уровень 3, Стандартизация:** Проектирование от контракта с машиночитаемыми спецификациями задокументировано и соблюдается по всей организации; опубликованная политика вывода из обращения, единая семантика ошибок и обязательные идемпотентность, пагинация по курсору и ограничение частоты применяются к каждой новой конечной точке; общее руководство по стилю и ревью стандартов API держат интерфейсы согласованными между командами.
- **Уровень 4, Управление:** Портфель API измеряется и контролируется относительно базовых значений: автоматические проверки обратной совместимости блокируют каждое изменение в CI, а вы отслеживаете время до первого успешного вызова, объём обращений в поддержку по конечной точке, частоту ломающих изменений, число живых версий и использование по конечным точкам, так что решения о выводе из обращения и проектировании опираются на свидетельства, а не мнения. Каждый API управляемый продукт в каталоге с названным владельцем, а метрики запускают действие, когда сервис отклоняется от целевых значений.
- **Уровень 5, Оркестрация:** Стратегия API непрерывно улучшается и интегрирована по организации; каталог, шлюз, правила версионирования и шлюзы совместимости работают как одна система; организация регулярно выводит, консолидирует и пересматривает область интерфейсов по измеренному принятию и стоимости; стандарты стилей взаимодействия и версионирования адаптируются по мере смещения экосистемы, партнёров и технологий, а ломающие изменения редки и хорошо управляемы.

## Идеи для обсуждения

- Как вы решаете, достаточно ли стабилен внутренний API, чтобы публиковать его вовне?
- Каково правильное окно поддержки устаревших версий в вашем контексте и кто за него платит?
- Где GraphQL или gRPC должны заменить REST внутри и где они добавили бы больше сложности, чем пользы?
- Как обеспечивать согласованность API между многими автономными командами, не становясь узким местом?
- Как API, потребляемые ИИ, и интерфейсы инструментов для агентов должны изменить ваши соглашения проектирования?
- Какие автоматические проверки могут поймать обратно несовместимые изменения до выпуска?

## Главные выводы

- Проектируйте контракт первым; API это продукт и долговечное обещание.
- Обратная совместимость защищает потребителей; ломающие изменения требуют новых версий и путей миграции.
- Выбирайте REST, GraphQL, gRPC или события по соответствию взаимодействию, а не по моде.
- Встраивайте идемпотентность, пагинацию, ограничение частоты и единые ошибки с первого дня.
- Управляйте API как продуктами с владельцами, каталогами и сильным опытом разработчика.
